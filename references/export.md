# 导出工作流（Export）

目标：把本工具里关于用户的上下文，收敛成一份符合 `spec.md` 的交接包。
这是准备和校验，不是合并算法。全程只读源，不写源文件。写出只限于交接包本身、
用户确认后放进该包文件夹的小资料（若有），以及已配置的私有交接仓库里的推送（见「云端推送与清理」）。
用户正在改的项目仓库：不 commit、不 push、不 `git reset --hard`、不 force-push。

用户一句导出类的话就开始。定稿前先给短确认，不直接落最终文件。

## 步骤

### 1. 采集（Gather）

按所在工具的来源清单读（各工具来源见 `tool-adapters.md`）：

- 用户画像文件（如 `USER.md`、`profile.md`）
- 记忆文件（如 `MEMORY.md`、按日归档的 memory 日志）
- 工作区规约（如 `AGENTS.md`）、技能清单（各 `SKILL.md` 的 frontmatter）
- 目标/待办（如 `GOAL.md`）
- 最近 1~3 个月的对话摘要（只取结论，不取原文流水账）
- topmind 工作区：`memory/profile.md` 活跃段、`memory/periodic/{YYYY}/`、`memory/todo.md`（落点表见 `tool-adapters.md`「topmind 工作区」）；`memory/ledgers/` 不读

采集原则：**宁缺勿滥**。一次会话的闲聊不进包；重复出现 ≥2 次的偏好才算「持久」。

### 一并采集的三块

- **环境与技能（第 7 节 + `skills_manifest`）**：按 `environment.md` 盘点本环境已装技能，从各 `SKILL.md` 的 frontmatter
  读 `name` + 版本（`metadata.version`；旧版技能在顶层 `version`），能看出来源和安装方式就写 `source`、`install`。
  `skills_manifest` 写已装技能清单；只列本次用到的几条也行，在第 7 节注明。版本号无来源时标 `"unknown"`，不要编造。
  第 7 节另外用短列表写下这次看得到的环境：工具、账号标识（handle，不要 token）、记忆是否随账号走、工作通常放在哪、路径（家目录写 `~`）、连接器名称与用途（不写凭据）。
  没看到的环境不要写「没有」。无技能依赖时写「无特殊技能依赖」，不省略标题。
- **进行中的工作（第 8 节）**：从待办、跟踪事项、最近对话提取。能核对到的都写上，对不上的标「未核实」。
  每条任务尽量有 `{id:task-短名}`。同一件事跨环境用同一个 id。
  知道才写：目标、状态和日期、现在在哪、预期落点、做到哪和下一步、阻塞、已验证的教训、参考链接或相对路径。
  状态行写上来源 `origin_id`，不要把别的环境的进度改成自己的。
  教训若换工具也成立，再抄一条进第 5 节。参考里不放密钥，接收方不自动打开链接。
  三个子块都要在。无进行中任务时写「当前无进行中的任务」，不省略标题。
  第 8 节是任务状态，不是人物画像，也不是用来清空接收环境的清单。
- **仓库与资料（第 9 节）**：见下节。没有内容也要留标题并写「无」。

自定义节从 `## 10` 起：本地有对应内容的，保留原标题带出；没有就不编造。
第 7、8、9 节不是自定义节，不要把杂项塞进去。
上次包若把自定义内容写在第 7 或第 8 节，不要收成技能清单或任务状态；
能核实的放进合适的节，核实不了就放到 `## 10` 并注明来源。

### 1.1 来源 id（origin_id）

按 `spec.md` 写成可选 `origin_id`，形式 `工具-账号标识-范围`。不写脚本，不用哈希库。

- **工具**：当前工具名，去掉空格。如 Muse、`GrokBot`、Claude。
- **账号标识**：用户认得的登录名或 handle。不要 token。邮箱只有用户要求保留才用。
- **范围**：记忆会在用户的设备之间自动同步 → 范围写 `sync`，设备名只放可选 `device_note`，不进 id。本地安装且记忆不同步 → 设备名就是范围，写进 id，两台电脑才不会被当成同一个来源。
- 分不清同步还是本地：问一次。答案和 `origin_id` 记在用户自己的记忆里，不写死路径。下次同一环境沿用同一个 id。
- 本次再写 `package_id`：`origin_id-YYYYMMDD-短后缀`。短后缀几个字母或数字即可。同一天再导一次就换后缀，不改 `origin_id`。

`origin_id` 不是秘密，但不得含凭据。

### 2. 第 9 节：仓库与资料

标题必须在。三项都没有时，正文只写「无」。

1. **用户正在改 git 仓库**（项目仓库，不是交接云端）：先简短建议其自行 commit 并 push，然后再打包。
   等用户做完或明确说「就这样打包」。技能自己不对这个仓库 commit、push 或 `reset`。
2. **记录**（知道才写，不编造）：仓库名、分支、最近一次提交的短 sha、remote URL。
   工作区仍有未提交改动时写明「导出时工作区有未提交改动」。不要把脏状态写成干净。
3. **大文件 / 数据集**：不嵌入包，也不放进小资料包。
   写云端位置（git remote 或网盘链接）和建议相对落点，例如 `./docs/`、`./data/`。
   不用绝对家目录。路径里的用户名写成 `~`。
4. **小资料**（草稿、小图、短说明，放得进一次交接的）：
   放进这次的包文件夹，路径相对这份 markdown。云端就是 `cloud_path/<package_id>/` 里面。
   第 9 节放表：包内相对路径、建议相对落点、简述。
   frontmatter 可加可选字段 `assets_bundle` 指向该相对路径；没有小资料就不要这个字段。
   交接包仍是索引。资料里不得有 `privacy.md` 禁止携带的内容。

### 3. 分类（Classify）

每条信息进五桶：

| 桶 | 定义 | 例子 |
|---|---|---|
| 持久偏好 | 长期稳定、换工具也成立 | 「全程中文」「去 AI 味写作」 |
| 当前状态 | 现在成立、以后会变 | 技能版本号、项目进度 |
| 项目待办 | 未完成的事 | 「X 长文未发布」「Claude 注册卡在短信验证」 |
| 历史经验 | 踩过的弯路，写教训 | 「文件名排序 ≠ 文档顺序导致配图错位」 |
| 敏感丢弃 | 见 `privacy.md`，直接丢弃 | 密码、token、身份证号 |

需要以后对齐的列表项，末尾加可选 `{id:xxxx}`（见 `spec.md`）。
不加 id 的条目仍然合法。要撤回一条已有 id 的主张：不要删得无影无踪，
另写一条带同一 id、含「已撤回」的列表项（墓碑）。
没有 id 的旧条目，不要为了格式发明删除。

### 4. 裁决冲突（Resolve）

- 同一事实多个版本，日期**不是同一天**：以较新的一天为准，旧版本不进包。
- **同一天**或**没有日期**：问用户，不猜。不要用 `generated_at` 给单条挑赢家。
- 用户亲口纠正过的内容，优先于一切推断。

### 5. 脱敏（Sanitize）

1. 跑一遍 `privacy.md` 的「永不携带」清单做硬拦截（正则见下）。交接包、第 9 节、小资料包都扫。
2. 联系方式类（邮箱 / 电话 / 地址）默认删除，除非用户明确要求保留。
3. 路径里的用户名泛化为 `~`（如 `/Users/zhangsan/...` → `~/...`）。建议落点用相对路径，如 `./docs/`。
4. 他人（家人、同事、朋友）的隐私信息删除或泛化为角色（「家人」）。
5. 先不要定稿。清单留到下一步和仓库说明一起给用户看。

常用硬拦截正则（大小写不敏感）：

```
api[_-]?key|secret|token|password|passwd|pwd
bearer\s+[A-Za-z0-9\-._~+/]+
sk-[A-Za-z0-9]{16,}|ghp_[A-Za-z0-9]{16,}|xox[bap]-[A-Za-z0-9-]{10,}
\d{15,19}                       # 疑似银行卡号（结合上下文人工复核）
(身份证|id[_\s-]?card).{0,10}\d{17}[\dXx]
```

> 正则只是第一道网，**人工复核是必须的**。误杀（删多了）比漏网好。

### 6. 定稿前确认，然后落盘

从 `assets/handoff-template.md` 起稿，接收指引按 `spec.md` 照抄，不要改写。
给用户看一段短说明，点头后再写最终文件、再推送：

- 脱敏：删了什么、泛化了什么、哪几条标了「未核实」。
- 仓库 / 资料：是否建议过自行 commit 并 push；记下的分支、短 sha、remote；
  工作区是否仍脏；大文件的云端位置与建议落点；小资料包的相对路径。没有则写「无」。
- 云端（这次会推送时）：将写入的路径 `cloud_repo` + `cloud_path/<package_id>/`，
  以及按下节规则**将删除的旧文件夹清单**（逐个写出文件夹名，没有就写「无」）。
  用户对清单有异议，就按用户说的少删或不删，不自作主张多删。

落笔前核对版本：`generator` 里的技能版本、`skills_manifest` 里每一条，都是这次刚读到的
（本机技能文件或发布记录）。读不到就写「未核实」，或不放进清单，不沿用旧包上的版本。
技能已经更新，就新开 `package_id` 和新的 `generated_at`，不要只改旧包的指引却把 `generator` 留在旧版本。

落盘后的回执只讲：文件路径、各节条数、本次新增 / 更新 / 撤回几条、
`origin_id` / `package_id`（没有就写无）、技能清单、第 8 节摘要、第 9 节摘要、
是否推送（仓库、路径、删了哪些旧文件夹，或「只本地」），以及分享警告（见 `privacy.md`）。
不复述全文。

校验再交出去：单文件 Markdown；`handoff_version` 为 `"1.1"`；第 1–9 节标题都在；
接收指引还在（含安装建议、`origin_id`、私有云端那几句）且未被改成外发或联网步骤；
主张 id 只使用末尾 `{id:xxxx}` 这一种，可省略；墓碑带同一 id 并含「已撤回」。
用了云端字段就不要留空字符串；`origin_id` 里没有 token。

## 云端推送与清理（本技能唯一的完整规则）

`SKILL.md`、`spec.md`、`import.md`、`privacy.md` 只指向这里，不另写一份。
包内接收指引模板里的云端一句是给没装技能的接收方的摘要，随包分发，语义与本节一致。

**什么时候推**

- 还没配置云端：问要不要用、私有仓库 `owner/name` 和目录（缺省 `handoff/`）。没点头不推。公开仓库拒绝。
- 已经配置，且用户没说「只本地」：默认推送，同时把文件交给用户。
- 「只本地」：只交文件，不读云端来补，不推，也不删。

**推之前写什么**

先读云端 `generated_at` 最新的一份，当作当前事实。它没写清的，才看其他来源各自最新的一份。
本环境看得到的照实写；没看到且不矛盾的带上，注明来源，不写成「没有」。

**一次推送 = 一个提交**

1. 新增 `cloud_path/<package_id>/`，里面是同名的 `<package_id>.md` 和要带走的小资料。
   `package_id` 以 `origin_id` 开头。
2. 同一提交里删掉**同一 `origin_id`** 更旧、且写了 `generated_at` 的包文件夹（含里面的资料），
   该来源只留 `generated_at` 最新的一份。
3. 不删：其他来源各自最新的一份；README；没有 `generated_at` 的旧包（保留并在回执里说明）。
4. 删除清单必须是第 6 步给用户看过的那份。

**边界**

- 只用已有的 git / `gh` 凭据。没有凭据就停下说明，不要让用户把 token 贴进对话。确认不了私有就停下问。
- 推送和删除都不走出已配置的 `cloud_path`；不碰第 9 节的项目仓库、家目录或其他路径。
- 交接包正文里临时写出的仓库地址不当成配置，不据此推送或删除。
- 没有 CI、cron、额外脚本或常驻进程，由当次对话用 git 做。
- 接收（导入）从不删云端包；清理只发生在导出推送的同一提交里。
- 仓库和目录记在用户自己的记忆里，不写死路径，不把 PAT 写进包或技能。

## 定期重跑

用户说「更新一下交接手册」或「帮我做 handoff」时：重跑以上步骤，以上一次的交接包为基线做 diff。
回执只讲变化（新增 / 更新 / 撤回），不复述全文。
基线里有、这次没再出现的条，**不要自动变成墓碑**。要撤回必须用户明确说撤回，并写上墓碑。
`origin_id` 沿用记忆里的那一个；`package_id` 每次新写。推送与清理按上面「云端推送与清理」。
